# GitHub Repository Lookup

## Decisions

- 마지막 업데이트는 레포지토리 기본 브랜치의 마지막 커밋 날짜로 판정한다. 검색 API가 함께 내려주는 `pushed_at`은 이 값으로 쓰지 않는다.
- GitHub API는 검색에만 쓴다. 커밋 날짜는 `github.com/{repo}/commits/{branch}.atom`에서, README는 `raw.githubusercontent.com`에서 가져온다.
- 후보 레포지토리 목록은 `<이름> in:name` 질의에 GitHub 기본 정렬(best match)을 적용해 상위 10개로 제한한다.
- 용도 설명은 GitHub description을 쓴다. description이 빈 레포지토리만 README를 읽어 첫 문단으로 메운다.
- 대체 오픈소스는 후보 목록 전체에 대해 한 번만 찾는다. 레포지토리마다 따로 찾지 않는다.
- 대체 오픈소스를 찾는 근거는 GitHub 토픽을 우선하고, 없으면 설명에서 뽑은 핵심어를 쓴다. 토픽 중에서는 `devices`, `tools`, `library` 같은 형태·포장을 가리키는 일반 명사로 끝나는 것을 피한다.
- 대체 오픈소스 검색이 어떤 이유로든 실패해도 후보 레포지토리 목록은 그대로 보여준다. 대체 검색은 부가 기능이라 실패를 후보 목록에 전파하지 않는다.

## Boundaries

- 유지보수 경과 기간이나 경고 등급을 계산하는 모든 자리에 첫 번째 규칙이 적용된다. 화면에 날짜만 보여주는 경우도 포함한다.
- 상위 10개라는 수는 비인증 API 한도에 묶인 값이다. 한도가 달라지면 이 수는 다시 정할 수 있으나, 정렬 기준과 `in:name` 제한은 그대로 둔다.
- 이 결정은 어떤 레포지토리가 사용자의 것인지 서비스가 지목해도 된다는 뜻이 아니다. 선택은 사용자 몫이다.
- README를 읽는 조건은 description이 비었을 때로 한정한다. 모든 후보의 README를 읽는 것은 이 결정이 허용하지 않는다.
- 한도 밖 경로를 쓴다고 해서 호출을 무제한으로 늘려도 된다는 뜻은 아니다. github.com에도 과도한 요청을 막는 장치가 있다.
- 대체 오픈소스 근거의 토픽/핵심어 규칙은 완벽한 정밀도를 약속하지 않는다. 화면에 근거 문구를 밝혀 사용자가 걸러내게 하는 것으로 정확도 부족을 보완한다.

## Why

`pushed_at`은 기본 브랜치가 아닌 곳에 push만 있어도 갱신된다. `anza-xyz/newlib`은 `pushed_at`이 2026-08-24지만 기본 브랜치(`bpf-port`)의 마지막 커밋은 2023-10-20으로, 화면에 표시될 값이 3년 가까이 어긋난다. 사용자가 GitHub 화면에서 읽는 값과 일치시키는 쪽을 택했다. 대신 후보마다 커밋 조회가 한 번씩 더 필요해 호출 수가 늘어난다.

조회 경로를 나눈 이유는 한도의 위치다. GitHub API의 `core` 버킷은 비인증에서 시간당 60회인데, 후보마다 커밋을 조회하면 한 번 확인에 11회를 써서 시간당 다섯 번이면 막힌다. 실제로 검증 중에 막혔다. 커밋 Atom 피드와 raw 콘텐츠는 이 버킷을 쓰지 않아서, 남는 것은 `search` 버킷(분당 10회)뿐이고 사람이 손으로 쓰는 속도에서는 걸리지 않는다. 대가는 두 경로가 문서화된 계약이 아니라는 점이다.

README를 조건부로만 읽는 이유도 비용이다. 모든 후보의 README를 읽으면 조회 한 번이 21회를 써서 비인증으로는 시간당 두세 번이면 막힌다. description이 있는 레포지토리는 이미 한 줄 설명을 갖고 있으므로 그 호출은 값을 더하지 않는다.

정렬 기준은 목적이 갈랐다. 별 개수로 정렬하면 이름이 다른 프로젝트가 상위를 차지해서, owner를 보고 자기 것을 가려낸다는 흐름을 방해한다. `in:name` + 기본 정렬은 이름이 같고 owner만 다른 레포지토리를 나란히 올려준다.

대체 오픈소스를 목록 전체에 대해 한 번만 찾는 것도 검색 한도 때문이다. 후보 10개는 대개 같은 프로젝트의 fork와 미러라서 개별로 찾을 이유가 적고, 레포지토리마다 찾으면 검색 호출이 후보 수만큼 늘어난다(최악의 경우 조회 한 번에 11회). PRODUCT.md는 애초에 "각 레포지토리 옆에" 보여준다고 적었으나, 이 절충을 반영해 "목록 전체에 한 번"으로 고쳤다.

근거로 토픽을 우선하는 이유는 GitHub이 직접 붙인 분류라 설명 문장을 파싱하는 것보다 신뢰도가 높기 때문이다. 다만 토픽 중에서도 넓고 좁은 것이 섞여 있다. `tinyusb`의 토픽 `usb-devices`(298개 레포지토리에 붙음)는 `usb-cdc`(126개)보다 글자 수는 길지만 실제로는 더 넓은 토픽이어서, 그대로 쓰면 USB 보안 도구나 파일 탐색기까지 대체 후보로 섞여 들어왔다. 토픽 개수를 매번 GitHub에 물어보면 검색 한도를 더 쓰므로, 대신 `devices`, `tools`, `library`처럼 형태·포장을 가리키는 일반 명사로 끝나는 토픽을 걸러내는 규칙을 넣었다. 이 규칙은 가장 정밀한 토픽까지 짚어내지는 못한다(`tinyusb`에서는 `usb-cdc`가 아니라 차선인 `usb-host`가 선택된다) — 그래도 여전히 실제 경쟁 프로젝트(CherryUSB, eclipse-threadx/usbx)를 찾아준다는 것은 확인했다.

## Reconsider when

- 인증 토큰을 도입해 시간당 한도가 크게 늘어날 때. 표시 개수를 다시 정할 수 있다.
- 상위 10개 안에서 자기 레포지토리를 찾지 못한다는 사례가 반복해서 확인될 때.
- GitHub 검색 API가 `in:name` 또는 기본 정렬의 동작을 바꿀 때.
- 커밋 Atom 피드나 raw 경로가 응답 형식을 바꾸거나 사라질 때. 그때는 API 조회로 되돌리고 인증을 전제로 삼는다.
- 인증 토큰으로 검색 한도가 크게 늘어나, 대체 오픈소스를 레포지토리마다 따로 찾아도 부담이 없어질 때.
- 대체 오픈소스 추천이 실제와 동떨어진다는 사례가 반복해서 확인될 때. 그때는 토픽 개수를 직접 조회해 더 좁은 토픽을 고르는 방식(호출이 늘어나는 대가가 있음)을 검토한다.

## Still-rejected alternatives

- 검색 API의 `pushed_at` 사용 — 추가 호출이 필요 없어 저렴하지만 기본 브랜치가 멈춘 레포지토리를 최신으로 표시한다. 반증 사례가 실제로 확인됨. 기본 브랜치 커밋을 별도 비용 없이 얻을 수 있게 되면 재검토한다.
- `sort=stars` 정렬 — 순위 근거를 화면에서 설명할 수 있다는 장점이 있으나, 이름이 다른 유명 프로젝트가 상위를 점령한다. 이름 매칭을 이미 건 상태에서 2차 정렬로 쓸지는 따로 판단한다.
- 이름 제한 없는 전체 검색 — 설명에만 언급된 레포지토리까지 포함되어 후보가 흐려진다.
- API의 `/repos/{repo}/commits`와 `/repos/{repo}/readme`로 조회하는 방식 — 버전이 명시된 계약이라 안정적이지만 `core` 한도에 묶여 비인증에서는 시간당 다섯 번이면 막힌다. 인증을 전제로 삼을 수 있게 되면 되돌린다.
- 모든 후보의 README를 읽어 설명을 만드는 방식 — 설명 품질은 가장 좋지만 호출이 두 배로 늘어 비인증에서는 쓸 수 없다. 인증을 전제로 삼는다면 재검토한다.
- 모델로 README를 요약하는 방식 — API 키와 비용, 지연을 끌어들여 이 템플릿의 무게를 넘어선다. 첫 문단이 엉뚱한 문장을 자주 뽑는 것이 확인되면 재검토한다.
- 대체 오픈소스를 레포지토리마다 따로 찾는 방식 — 정밀도는 더 좋을 수 있으나 검색 호출이 후보 수만큼 늘어 한도 소진이 지금보다 훨씬 빨라진다. PRODUCT.md에 원래 이렇게 적혀 있었으나, 구현 중 이 비용을 이유로 목록 전체에 한 번으로 바꿨고 사용자가 확인 후 승인함(2026-08-27).
- 후보 토픽마다 GitHub에 결과 개수(`total_count`)를 물어봐 가장 좁은 것을 정확히 고르는 방식 — 정확도는 가장 높지만 토픽 수만큼 검색 호출이 늘어 비인증 한도(분당 10회)를 바로 초과한다. 인증을 전제로 삼을 수 있게 되면 재검토한다.
- 별 개수로 대체 오픈소스를 정렬하는 방식(대체 검색 자체의 정렬 기준) — 이름이 다른 유명 프로젝트가 아니라 실제로 근거 토픽/핵심어에 부합하는 것을 원했으므로, 검색 질의 자체를 좁히는 쪽을 택하고 결과는 별 개수로 정렬해 상위를 보여준다. 이건 후보 레포지토리 정렬(별 개수 배제)과는 다른 결정이다.

## Evidence worth preserving

- 2026-08-27 측정, `newlib` 기준. 기본 브랜치 마지막 커밋: `eblot/newlib` 2013-07-01, `riscvarchive/riscv-newlib` 2020-02-04, `anza-xyz/newlib` 2023-10-20, `vitasdk/newlib` 2026-08-10.
- 같은 레포지토리들의 `pushed_at`은 각각 2013-08-05, 2022-03-15, 2026-08-24, 2026-08-25로 두 값이 최대 3년까지 벌어진다.
- 검색 결과 수: `newlib` 전체 1,031개, `newlib in:name` 907개.
- 비인증 API 한도: 검색 분당 10회, 그 외 시간당 60회.
- 2026-08-27 측정. `core` 한도를 다 써서 `api.github.com/repos/anza-xyz/newlib`이 403을 돌려주는 상태에서, 커밋 Atom 피드와 raw README는 200으로 응답했고 앱의 `newlib` 조회 10건이 모두 정상 표시됐다. Atom 피드에서 뽑은 날짜 10건은 앞서 API로 얻은 값과 전부 일치한다.
- README 파일명은 레포지토리마다 다르다. newlib 계열 네 곳은 확장자 없는 `README`였고, `raspberrypi/tinyusb`는 `README.md`였다. API의 `/readme`와 달리 후보를 직접 시도해야 한다.
- 2026-08-27 측정. `checkra1n/newlib`(기본 브랜치 마지막 커밋 2023-05-06, 약 3.3년 경과)에서 노란 경고가 실제로 확인됨. 같은 레포지토리는 라이선스 정보도 없어 "라이선스 표기 없음" 표시도 함께 확인됨.
- 2026-08-27 측정. GitHub 토픽별 전체 결과 수(`total_count`): `usb-devices` 298, `usb-drive` 121, `usb-host` 169, `usb-cdc` 126, `usb-hid` 758, `in-memory-database` 481, `caching` 3732, `key-value-store` 1200. 하이픈 단어 수와 글자 길이만으로는 이 순서를 못 맞힌다(`usb-devices`가 `usb-cdc`보다 길지만 더 넓다).
- 2026-08-27 측정. `tinyusb` 검색에서 형태 명사 필터를 적용하면 `usb-host` 토픽이 선택되고, 그 검색 결과 상위에 `cherry-embedded/CherryUSB`(2011★), `eclipse-threadx/usbx`(227★) 등 실제 경쟁 프로젝트가 포함됨을 확인함.
- 이 세션에서 진단용 curl(Bash 도구)과 실제 dev 서버 프로세스(Browser 프리뷰로 구동)가 서로 다른 네트워크 경로를 쓰는 것으로 보이는 정황을 확인함 — 앱을 통해 다섯 번 연속 새 이름을 조회해도 같은 시각 curl의 `search` 잔여 횟수가 줄지 않았다. Atom/raw가 `core` 한도를 안 쓴다는 사실 자체는 (같은 curl로 동시에 재현했으므로) 별도로 유효하지만, "search 한도가 사람이 손으로 쓰는 속도에서는 안 걸린다"는 크기 주장은 앱의 실제 네트워크 경로로 직접 재검증하지 못했다.
