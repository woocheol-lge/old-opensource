# Pin Repository by Link

## Decisions

- 이름 검색과 링크 확인을 입력칸 하나로 받는다. 별도 입력칸이나 별도 URL 파라미터를 두지 않는다.
- 입력값이 `owner/repo` 표기나 GitHub 링크로 알아볼 수 있으면(`parseGithubFullName`이 성공하면) 레포지토리 하나를 정확히 확인하고(single), 그렇지 못하면 이름으로 후보 여러 개를 찾는다(list).
- 레포지토리 하나를 정확히 확인할 때는 GitHub 검색 API의 `repo:` 한정자를 쓴다. `/repos/{owner}/{repo}`(core 버킷)로 바꾸지 않는다.
- owner 자리(문자열의 첫 세그먼트)에 점이 있으면 github.com이 아닌 도메인으로 보고 거부한다. repo 이름 자리의 점은 거부 사유로 보지 않는다.
- `repo:` 한정자가 422를 돌려주는 경우, 존재하지 않는다고 단정하지 않는다. "잘못된 링크입니다"로 실패를 알린다.
- `owner/repo`로 알아본 값이 확인에 실패하면(잘못된 형태, 존재하지 않음, 한도 초과, 기타 오류) 그 안내만 보여준다. 이름 검색으로 다시 물러서지 않는다.

## Boundaries

- list/single 분기는 입력값 하나로만 정해진다. "이름칸에는 이것, 링크칸에는 저것"처럼 두 값을 동시에 받는 경우 자체가 없다.
- 레포지토리 조회(single) 자체도 search 버킷을 쓰므로, 이름 검색(list)과 같은 한도(분당 10회)를 공유한다. 조회 한 번은 어느 모드든 검색 호출을 최대 2회(본 조회 1회 + 대체 오픈소스 1회) 쓴다.
- 점이 있는 레포지토리 이름을 링크로 확인하지 못하는 것은 GitHub 검색 자체의 한계이지 이 앱의 버그가 아니다. 이 한계를 완전히 우회하는 것은 범위 밖이다(스펙의 "범위 밖과 이유" 참고).

## Why

이 결정은 이전 시도의 실패에서 나왔다. 처음에는 이름 검색과 링크 확인을 별도 입력칸·별도 폼으로 두고, 폼을 다시 제출할 때 서로의 값을 숨은 필드로 실어 날랐다. 이 설계는 세 번 연달아 문제를 냈다.

1. 링크 입력칸에 브라우저 자동완성이 끼어들어, `https://github.com/anza-xyz/newlib`를 다 타이핑하기 전에 제출되면 `https://github.com/anza-xyz/n`처럼 잘린 값이 넘어갔다. `autocomplete="off"`로 막았다.
2. 그런데도 "여전히 자동으로 붙는다"는 재현 요청을 받아 다시 보니, 원인은 브라우저가 아니라 이 앱이었다. 한 번 URL에 박힌 `repo` 값을 이름 검색 폼의 숨은 필드가 계속 실어 날라, 이름만 다시 검색해도 예전 오류가 되풀이됐다. 이름 검색 폼이 링크 값을 안 가져오도록 비대칭으로 고쳤다.
3. 그런데도 다시 "화면에서 이름 검색창을 건드리지 않았는데 값이 나타난다"는 지적을 받았다. 실제 원인은 이름 검색창을 화면에서만(재제출 없이) 지운 뒤 링크 칸에 입력하고 제출하면, URL에는 여전히 예전 `q` 값이 남아 있어 링크 확인 폼의 숨은 필드가 그 스테일 값을 되살린다는 것이었다. 서버에 스냅샷된 값과 화면에 보이는 값이 어긋나는 근본 문제였다.

세 번째 문제를 제대로 고치려면 두 입력의 실시간 상태를 동기화하는 클라이언트 컴포넌트가 필요했다. 그 대신 사용자가 더 근본적인 해법을 제안했다: **애초에 입력칸을 왜 두 개로 나누는가?** 이름과 owner/repo 표기는 형태가 다르므로("슬래시가 있는가") 텍스트만 보고도 구분할 수 있다. 입력칸을 하나로 합치고 그 형태로 분기하면, 값 동기화라는 문제 자체가 사라진다. `parseGithubFullName`은 이미 이 판별 로직을 갖고 있었으므로(다른 목적으로 먼저 만들어둔 것을 재사용) 추가 구현 부담도 크지 않았다.

이 통합으로 예전에 있던 기능 하나가 자연히 사라졌다: "링크가 실패하면 이름 검색 결과를 이어서 보여준다." 입력칸이 하나뿐이므로 실패했을 때 물러설 별도의 "이름" 값이 없다. `owner/repo` 표기는 애초에 모호하지 않은 표기이므로, 그것이 실패하면 그 사실을 알리는 것으로 충분하다고 판단했다.

## Reconsider when

- 점이 있는 레포지토리 이름을 링크로 확인해 달라는 요청이 반복되면, `in:name` 검색 결과에서 정확히 일치하는 것을 걸러내는 방식(호출 1회 추가)을 검토한다.
- GitHub이 `repo:` 한정자의 점 처리 방식을 바꾸면 이 결정 전체를 다시 본다.
- `owner/repo` 형태로 입력했는데 사용자가 실제로는 이름 검색을 의도했다는 사례(예: 우연히 슬래시가 든 이름)가 반복되면, 자동 분기 대신 사용자가 직접 고르게 하는 방식을 재검토한다.

## Still-rejected alternatives

- 이름 검색과 링크 확인을 별도 입력칸·별도 폼으로 두고 서로의 값을 숨은 필드로 동기화하는 방식 — 세 번의 사고(자동완성 잘림, 실패한 링크 값의 되풀이, 화면에서만 지운 값의 부활)를 겪은 뒤 폐기했다. 실시간 동기화 없이는 "화면에 보이는 값"과 "서버가 아는 값"이 어긋나는 문제를 근본적으로 못 없앤다.
- 두 값을 동기화하는 클라이언트 컴포넌트(React state로 두 입력을 묶는 방식) — 문제를 고칠 수는 있었지만, 입력칸을 하나로 합치는 쪽이 문제 자체를 없애면서도 더 단순하다.
- 링크 확인 실패 시 이름 검색으로 물러서는 기능을 유지하는 방식 — 입력칸이 하나뿐인 구조에서는 물러설 별도의 "이름" 값이 없어 자연스럽지 않다. `owner/repo` 표기 자체가 모호하지 않으므로 실패 안내만으로 충분하다고 판단했다.
- `/repos/{owner}/{repo}`로 조회하는 방식 — core 버킷을 써서 기존 아키텍처(검색 버킷만 사용)와 어긋난다.

## Evidence worth preserving

- 2026-08-27 측정. `jashkenas/underscore.js`(실제 존재, 별 다수)로 재현: `GET /search/repositories?q=repo:jashkenas/underscore.js` → HTTP 422 "Validation Failed". `GET /search/repositories?q=underscore.js+in:name` → HTTP 200, total_count 171. `user:jashkenas underscore.js in:name`, `org:jashkenas underscore.js in:name` 조합도 각각 total_count 0, HTTP 0(빈 결과)로 정상 조회에 실패함.
- 2026-08-27 측정. 별도 폼 방식일 때, 이름 검색창을 화면에서만 지우고(재제출 없이) 링크 칸에 입력 후 제출하면 최종 URL이 `?repo=gcc-mirror/gcc&q=gcc-mirror/gcc`가 되어, 지운 값이 되살아나는 것을 실제 브라우저 조작(`form_input` + 실제 버튼 클릭)으로 재현함.
- 2026-08-27 측정. 입력칸을 하나로 합친 뒤: `?q=newlib` → 후보 15개(10+대안 5), 목록 모드. `?q=anza-xyz/newlib`와 `?q=https://github.com/anza-xyz/newlib` → 둘 다 레포지토리 하나만 확인하는 단일 모드로 정확히 분기됨. `?q=nobody-xyz-999/nothing-repo-999`(존재하지 않는 owner/repo) → "잘못된 링크입니다" 안내.
