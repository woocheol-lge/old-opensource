# Pin Repository by Link

## Decisions

- 이름 검색과 별도로, GitHub 링크나 `owner/repo` 표기를 넣어 레포지토리 하나를 정확히 확인하는 입력칸을 둔다. 검색창 바로 아래에 항상 보이며, 이름 검색 결과가 있어야만 나타나는 조건부 노출이 아니다.
- 레포지토리 조회는 GitHub 검색 API의 `repo:` 한정자를 쓴다. `/repos/{owner}/{repo}`(core 버킷)로 바꾸지 않는다.
- 링크 확인이 성공하면(정확히 레포지토리 하나를 찾으면) 이름 검색 목록은 보여주지 않는다. 이름 검색이 함께 입력되어 있어도 마찬가지다.
- 링크 확인이 실패하면(잘못된 링크, 존재하지 않음, 한도 초과, 기타 오류) "잘못된 링크입니다"로 시작하는 안내를 보여준다. 이름 검색이 함께 입력되어 있으면, "링크는 확인하지 못해, 오픈소스 이름으로만 검색된 결과입니다"라는 문구와 함께 이름 검색 결과를 그 아래에 보여준다.
- owner 자리(문자열의 첫 세그먼트)에 점이 있으면 github.com이 아닌 도메인으로 보고 거부한다. repo 이름 자리의 점은 거부 사유로 보지 않는다.
- `repo:` 한정자가 422를 돌려주는 경우, 존재하지 않는다고 단정하지 않는다. "확인하지 못했다"는 문구로 실패를 알린다.
- 이름 검색 폼을 제출하면 링크 확인 값은 가져오지 않는다. 반대로 링크 확인 폼을 제출하면 이름 검색 값은 그대로 가져온다 — 두 방향이 대칭이 아니다.

## Boundaries

- "이름 검색과 독립적으로 항상 보인다"는 배치 결정은 검색 한도 소비량과는 무관하다. 링크 확인 자체도 search 버킷을 쓰므로, 이름 검색과 링크 확인을 동시에 쓰면 조회 한 번이 검색 호출을 최대 4회(이름 검색 1회 + 이름 검색의 대체 오픈소스 1회 + 링크 확인 1회 + 링크 확인의 대체 오픈소스 1회)까지 쓸 수 있다.
- "링크 성공 시 이름 목록 숨김" 규칙은 화면에만 적용된다. 이름 검색 자체(GitHub 호출)는 여전히 실행되지 않는다 — `RepoResults`가 링크 확인을 먼저 시도하고, 성공하면 이름 검색을 아예 호출하지 않는다.
- 점이 있는 레포지토리 이름을 링크로 확인하지 못하는 것은 GitHub 검색 자체의 한계이지 이 앱의 버그가 아니다. 이 한계를 완전히 우회하는 것은 범위 밖이다(스펙의 "범위 밖과 이유" 참고).

## Why

애초 `PRODUCT.md`는 "검색에 잡히지 않은 레포지토리는 사용자가 직접 추가해서 같은 방식으로 확인할 수 있다"고만 적었고, 구체적인 화면 배치는 정하지 않았었다. 조건부 노출(이름 검색 결과 아래에 "못 찾으셨나요?" 형태로 노출)과 항상 노출(검색창 바로 아래에 독립된 입력칸) 중, 사용자가 직접 "검색창 바로 아래, 항상 보임"을 선택했다(2026-08-27). 정확한 링크를 이미 아는 사용자가 이름 검색을 거칠 필요가 없다는 이유였다.

이름 검색 목록을 링크 성공 시 숨기는 것도 사용자가 직접 지적한 결함에서 나왔다. `vite`를 이름과 링크 양쪽에 넣었을 때, 링크로 정확히 찾은 `vitejs/vite`가 그 아래 이름 검색 목록에도 첫 번째 항목으로 다시 나타나 중복되고 헷갈렸다. "링크로 확인한 경우에는 정확한 레포지토리이고 그것에 대한 대체 오픈소스이니 두 번째 목록이 필요 없다"는 사용자의 판단을 그대로 반영했다. 링크가 실패했을 때는 반대로 이름 검색 결과가 유일한 단서이므로 보여주되, 그 결과가 "링크가 아니라 이름으로만 찾은 것"임을 분명히 밝혀 사용자가 착각하지 않게 한다.

두 폼 사이의 값 보존을 비대칭으로 만든 것도 실제 사고에서 나왔다. 처음에는 양쪽 다 서로의 값을 숨은 필드로 실어 날랐다. 그런데 링크 입력칸에 브라우저 자동완성이 끼어들어 `https://github.com/anza-xyz/newlib`를 다 못 타이핑하고 `https://github.com/anza-xyz/n`처럼 잘린 채로 제출되는 사고가 났고, `autocomplete="off"`로 그 원인은 막았다. 그런데도 사용자가 "여전히 자동으로 붙는다"고 재현을 요청해 다시 보니, 원인은 브라우저가 아니라 이 앱이었다. 한 번 URL에 박힌 잘못된 `repo` 값을, 그 뒤로 이름 검색만 다시 실행해도 이름 검색 폼의 숨은 필드가 계속 실어 날라 "잘못된 링크입니다"가 되풀이됐다. 이름 검색 제출은 "이름으로 새로 찾겠다"는 의도이므로, 그 시점에는 링크 값을 놓아주는 쪽이 자연스럽다.

`repo:` 한정자를 쓰는 이유와 점이 있는 이름에서 실패하는 이유는 `github-repository-lookup.md`의 같은 종류 결정(검색 버킷 유지)과 얽혀 있지만, 이 결정은 "레포지토리 하나를 정확히 짚는" 별도 기능이라 여기 따로 남긴다. `repo:jashkenas/underscore.js`는 실제로 존재하는 레포지토리인데도 422(Validation Failed)를 돌려준다. `user:jashkenas underscore.js in:name`처럼 다른 한정자와 조합해도 마찬가지였다. 반면 점을 포함한 이름도 `in:name`(이름 검색이 쓰는 방식)으로는 정상 검색된다. 즉 문제는 이 앱의 파싱이 아니라 GitHub `repo:` 한정자 자체의 한계다. 이걸 완전히 우회하려면 `in:name` 검색 결과에서 owner와 이름이 정확히 일치하는 항목을 걸러내는 방식이 필요한데, 검색 호출이 하나 더 늘어나는 대가가 있어 지금은 정직한 안내로 대신한다.

## Reconsider when

- 링크 확인이 자주 쓰이는데 이름 검색과 동시에 쓰는 경우가 드물다는 게 확인되면, "항상 보임" 대신 조건부 노출로 되돌릴 근거가 될 수 있다.
- 점이 있는 레포지토리 이름을 링크로 확인해 달라는 요청이 반복되면, `in:name` 검색 결과에서 정확히 일치하는 것을 걸러내는 방식(호출 1회 추가)을 검토한다.
- GitHub이 `repo:` 한정자의 점 처리 방식을 바꾸면 이 결정 전체를 다시 본다.

## Still-rejected alternatives

- 이름 검색 결과 아래에 "내 레포지토리를 못 찾으셨나요?" 형태로 조건부 노출 — 사용자가 이미 정확한 링크를 알고 있을 때도 이름 검색을 먼저 거치게 만든다. 항상 보이는 독립 입력칸을 택함.
- 링크 성공 여부와 무관하게 이름 검색 목록을 항상 함께 보여주는 방식 — 정확한 레포지토리와 애매한 후보 목록이 뒤섞여, 같은 레포지토리가 두 번 나오는 등 혼란을 준다는 것이 실제로 확인됨(2026-08-27, `vite` 사례).
- `/repos/{owner}/{repo}`로 조회하는 방식 — core 버킷을 써서 기존 아키텍처(검색 버킷만 사용)와 어긋난다.
- `repo:owner/name`에서 점을 이스케이프하거나 따옴표로 감싸는 방식 — 시도했으나 403(한도 소진으로 추가 검증 중단)까지 겪었고, 이전 시도들은 여전히 422였다. 안정적인 우회로라는 확신이 없어 채택하지 않았다.

## Evidence worth preserving

- 2026-08-27 측정. `jashkenas/underscore.js`(실제 존재, 별 다수)로 재현: `GET /search/repositories?q=repo:jashkenas/underscore.js` → HTTP 422 "Validation Failed". `GET /search/repositories?q=underscore.js+in:name` → HTTP 200, total_count 171. `user:jashkenas underscore.js in:name`, `org:jashkenas underscore.js in:name` 조합도 각각 total_count 0, HTTP 0(빈 결과)로 정상 조회에 실패함.
- 2026-08-27 측정. `?q=vite&repo=https://github.com/vitejs/vite`를 동시에 넣었을 때, 수정 전에는 링크 확인 카드(1개+대안 5개)와 이름 검색 목록(10개+대안 5개)이 함께 나타나 `vitejs/vite`가 두 번 보였다. 수정 후에는 링크 확인 결과만 6개 카드로 나타나고 이름 검색 문구는 0회 등장함.
- 2026-08-27 측정. `?q=vite&repo=이건링크아님`(잘못된 링크 + 이름 검색 동시)에서는 "잘못된 링크입니다"와 "링크는 확인하지 못해, 오픈소스 이름으로만 검색된 결과입니다"가 둘 다 나타나고, 그 아래 이름 검색 목록("이름이 일치하는 레포지토리")도 정상 표시됨을 확인함.
- 2026-08-27 측정. `?q=newlib&repo=https://github.com/anza-xyz/n`(브라우저 자동완성이 잘라낸 값으로 실제 접속) 상태에서, 수정 전에는 이름 검색 폼 안에 `<input type="hidden" name="repo" value="https://github.com/anza-xyz/n">`이 들어 있어 "확인"만 다시 눌러도 같은 오류가 되풀이됐다. 수정 후에는 이름 검색 폼 안에 해당 hidden 필드가 없음을 확인함. 링크 확인 폼 안의 hidden `q` 필드는 그대로 유지됨.
