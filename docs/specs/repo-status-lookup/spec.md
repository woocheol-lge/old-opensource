# 오픈소스 이름으로 레포지토리 상태 확인하기

## 사용자 결과

오픈소스 이름을 입력하면 그 이름을 가진 GitHub 레포지토리 후보가 한 화면에 나열되고, 각 후보에서 owner와 이름, 생성일, 마지막 업데이트, 경고 등급, 라이선스, 한 줄 설명을 함께 확인한다. 사용자는 owner를 보고 자기가 쓰는 레포지토리를 골라, 그것이 얼마나 오래 방치됐는지를 다른 탭을 열지 않고 파악한다. 이미 아는 레포지토리라면 같은 입력칸에 `owner/repo` 표기나 GitHub 링크를 넣어, 애매한 목록 없이 그 레포지토리 하나만 바로 확인한다.

## 범위

- 이름, `owner/repo` 표기, GitHub 링크를 모두 받는 입력칸 하나와 검색 실행.
- 입력값이 `owner/repo`나 GitHub 링크로 알아볼 수 있으면 그 레포지토리 하나만 정확히 확인하고, 그렇지 않으면 이름으로 후보 여러 개를 찾는다.
- 후보 레포지토리 목록 표시. 각 항목은 owner, 레포지토리 이름, 생성일, 마지막 업데이트, 경고 등급, 라이선스, 설명, GitHub 원본으로 가는 링크를 담는다. 레포지토리 하나만 정확히 확인했을 때도 같은 항목을 담는다.
- 설명은 GitHub description을 쓰고, 그것이 비어 있는 레포지토리만 README 첫 문단으로 메운다.
- 경과 기간에 따른 경고 등급 표시.
- 후보 목록(또는 정확히 확인한 레포지토리 하나)에 대해 비슷한 기능을 하는 오픈소스를 한 번 찾아, 근거(GitHub 토픽 또는 설명 핵심어)와 함께 표시. 레포지토리마다 따로 찾지 않는다.
- 결과 없음, 호출 실패, API 한도 초과 상황의 안내.

## 수용 기준

- 이름을 입력하고 검색하면 후보 레포지토리가 최대 10개 나열된다.
- `newlib`을 입력하면 목록의 모든 항목이 이름에 `newlib`을 포함하고, 항목마다 owner가 서로 다르게 보인다.
- 각 항목에 생성일과 마지막 업데이트가 날짜로 보인다. 마지막 업데이트는 해당 레포지토리 기본 브랜치의 마지막 커밋 날짜다.
- 마지막 업데이트로부터 5년 이상 지난 항목은 빨간 경고로, 3년 이상 5년 미만은 노란 경고로 표시된다. 3년 미만은 경고가 붙지 않는다.
- `newlib` 검색 결과에서 `eblot/newlib`(2013-07-01)과 `riscvarchive/riscv-newlib`(2020-02-04)은 빨간 경고가, `checkra1n/newlib`(2023-05-06)은 노란 경고가 붙고, `anza-xyz/newlib`(2023-10-20)과 `vitasdk/newlib`(2026-08-10)은 경고가 붙지 않는다.
- description이 비어 있는 레포지토리는 README 첫 문단이 설명 자리에 보인다. README도 없거나 읽지 못하면 설명이 없다는 사실이 드러난다.
- 각 항목에 라이선스가 보인다. GitHub에 라이선스 정보가 없는 레포지토리는 "라이선스 표기 없음"으로 드러나고, 유지보수 경고와 같은 빨간색으로 강조된다.
- 각 항목에서 GitHub 원본 레포지토리로 이동할 수 있다.
- 대체 오픈소스를 찾으면 후보 목록(또는 레포지토리 하나) 아래에 한 번만 나타나고, 어떤 근거로 찾았는지 문구로 밝힌다. 찾지 못하거나 대체 검색 자체가 실패해도 이 구역만 보이지 않을 뿐, 이미 찾은 결과는 그대로 보인다.
- `anza-xyz/newlib`처럼 `owner/repo` 표기를 넣거나 그 GitHub 링크를 넣으면, 이름이 `newlib`인 다른 9개는 보이지 않고 그 레포지토리 하나만 카드로 보인다(생성일·마지막 업데이트·경고·라이선스·설명은 후보 카드와 동일한 형식). 아래에 그 레포지토리에 대한 대체 오픈소스가 이어진다.
- `owner/repo` 표기로 알아본 값인데 GitHub에서 확인하지 못하면(존재하지 않음, 한도 초과, 기타 오류) "잘못된 링크입니다"로 시작하는 안내만 보인다. 이름 검색으로 다시 물러서지 않는다 — 입력값 자체가 이미 특정 레포지토리를 가리키고 있었기 때문이다.
- 결과가 하나도 없는 이름을 넣으면 결과가 없다는 안내가 보인다.
- GitHub API 한도에 걸리면 왜 결과를 못 불러왔는지 안내가 보이고, 화면이 빈 채로 멈추지 않는다.

## 확정된 제약과 근거

- 마지막 업데이트는 기본 브랜치의 마지막 커밋 날짜다. 검색 API의 `pushed_at`은 다른 브랜치 push에도 갱신되어 사용자가 GitHub 화면에서 읽는 값과 어긋난다.
- GitHub API는 검색에만 쓴다. 커밋 날짜는 커밋 Atom 피드에서, README는 raw 콘텐츠에서 가져와 시간당 60회 한도를 피한다.
- 후보 목록은 `<이름> in:name` 질의에 GitHub 기본 정렬을 적용한 상위 10개다. 별 개수 정렬은 이름이 다른 프로젝트를 상위로 올려 후보 판별을 방해한다.
- 어느 레포지토리가 사용자의 것인지 서비스가 지목하지 않는다. 판단은 사용자에게 남긴다.
- 경고는 알림까지다. 대체를 권하거나 조치를 대신하지 않는다.
- 대체 오픈소스는 후보 목록 전체(또는 정확히 확인한 레포지토리 하나)에 대해 한 번만 찾는다. 후보 대부분이 같은 프로젝트의 fork와 미러라 개별로 찾을 이유가 적고, 레포지토리마다 찾으면 검색 호출이 후보 수만큼 늘어 한도를 훨씬 빨리 소진한다. 근거는 GitHub 토픽을 우선하고, 없으면 설명의 핵심어를 쓴다.
- 입력값 하나로 두 경로를 나누는 기준은 `owner/repo` 표기(또는 GitHub 링크)로 알아볼 수 있는지 여부다. 알아보면 정확히 하나만, 그렇지 못하면 이름으로 여러 개를 찾는다. 입력칸이나 URL 파라미터를 이름용과 링크용으로 따로 두지 않는다 — 예전에 두 칸을 따로 두고 서로의 값을 숨은 필드로 실어 날랐더니, 화면에서 지운 값이 URL에는 남아 있다가 되살아나는 문제가 반복됐다.
- 정확히 확인하는 경로는 GitHub 검색 API의 `repo:` 한정자를 쓴다. 이 한정자는 이름에 점(`.`)이 있는 레포지토리(예: `underscore.js`)에서 실제로 존재해도 422를 돌려준다. 이 경우도 "잘못된 링크"로 안내하되, 존재하지 않는다고 단정하지 않는다.

근거의 상세와 재검토 조건은 `docs/decisions/github-repository-lookup.md`(후보 목록·대체 오픈소스)와 `docs/decisions/pin-repository-by-link.md`(링크 확인)에 있다.

## 가정

되돌리기 쉬운 선택이며, 필요하면 구현 중에 바꿀 수 있다.

- 환경변수에 GitHub 토큰이 있으면 검색을 인증 호출로 보내고, 없으면 비인증으로 동작한다.
- README 파일명은 `README.md`, `README`, `readme.md`, `README.rst`, `README.txt`를 한꺼번에 시도하고 먼저 걸리는 것을 쓴다.
- 용도 설명은 GitHub 레포지토리 description을 그대로 쓴다. description이 없을 때만 README를 읽으며, 뱃지와 제목과 코드 블록을 걷어낸 뒤 첫 문단을 쓴다.
- README 요약은 모델을 쓰지 않고 첫 문단을 잘라 쓴다. 모델 요약은 API 키와 비용, 지연을 끌어들여 이 템플릿의 무게를 넘어선다.
- 마지막 커밋 날짜를 가져오지 못한 항목은 날짜를 확인할 수 없다고 표시하고 경고 등급을 매기지 않는다.
- 경과 기간은 조회 시점의 오늘 날짜를 기준으로 계산한다.
- 검색은 사용자가 명시적으로 실행할 때만 일어난다. 입력하는 동안 자동으로 조회하지 않는다.

## 범위 밖과 이유

- 조회 결과 저장, 계정, 재방문 시 이어보기. `PRODUCT.md`가 일회성 조회 도구로 못박았다.
- 대체 오픈소스를 레포지토리마다 따로 찾는 것. 목록 전체에 한 번만 찾기로 확정했다(위 확정된 제약 참고). 검색 한도 부담이 지금(조회당 최대 2회)보다 크게 늘어난다.
- 점이 있는 레포지토리 이름을 링크로 확인하는 문제를 완전히 우회하는 것. `user:`/`org:` 한정자와 조합해도 GitHub 검색이 같은 방식으로 실패해, 손쉬운 우회로가 없다는 것을 확인했다. 정직한 안내로 대신한다.

## 미룬 결정

- 목록을 10개 너머로 더 보는 방법. 상위 10개에서 자기 레포지토리를 찾지 못하는 사례가 쌓이면 다시 꺼낸다.
- 아카이브된 레포지토리를 따로 표시할지 여부.
- 순위가 왜 이렇게 매겨졌는지 화면에서 설명할지 여부. GitHub 기본 정렬은 근거를 공개하지 않는다.
- 점이 있는 레포지토리 이름을 링크로 확인하는 것을 완전히 지원할지 여부. 지금은 정직한 안내로 대신하고, `in:name` 검색으로 후보를 찾아 정확히 하나로 좁히는 방식은 호출이 늘어나 미뤘다.

## 남은 위험

- 비인증 상태에서 조회 한 번이 GitHub 검색 한도(분당 10회)를 최대 2회(후보 검색 1회, 대체 오픈소스 검색 1회) 쓴다. 커밋 날짜와 README는 검색 한도에 걸리지 않는 경로로 가져오므로 별도로 세지 않는다.
- 커밋 Atom 피드와 raw 콘텐츠는 문서화된 계약이 아니다. GitHub이 형식을 바꾸면 날짜와 설명이 한꺼번에 "확인 불가"로 떨어진다.
- Atom 피드는 필요한 커밋 1건이 아니라 20건을 보낸다. 후보 10개면 응답이 200KB 안팎이 된다.
- README 첫 문단이 항상 그 프로젝트를 설명하지는 않는다. 뱃지 줄이나 설치 안내가 먼저 오는 README에서는 엉뚱한 문장이 뽑힐 수 있다.
- 상위 10개 안에 사용자의 레포지토리가 없을 수 있다. `newlib`에서는 5위로 확인됐지만 모든 이름에 대한 보장은 아니다.
- GitHub 기본 정렬은 내부 관련도 점수라서 같은 질의라도 순위가 달라질 수 있다. 수용 기준의 특정 레포지토리가 목록에서 빠지면 그 항목이 아니라 정렬 기준을 다시 봐야 한다.
- "비슷한 기능"의 근거(토픽 우선, 없으면 설명 핵심어)는 완벽히 정확하지 않다. `tinyusb` 검색에서는 형태를 가리키는 일반 토픽(`usb-devices`)을 걸러내는 규칙을 넣었지만, 가장 정밀한 토픽(`usb-cdc`)까지 짚어내지는 못하고 차선(`usb-host`)을 고른다. 그래도 실제 경쟁 프로젝트를 찾아준다는 것은 확인했다.
- 이름에 점이 있는 실제 레포지토리(`underscore.js`, `socket.io`, `p5.js` 등)는 링크로도 확인할 수 없다. GitHub 검색의 `repo:` 한정자 자체가 이런 이름에 422를 돌려주기 때문이다. "잘못된 링크입니다"로 안내하지만, 사용자 입장에서는 분명히 존재하는 레포지토리인데 확인이 안 되는 것으로 보일 수 있다.
